# 오늘의 진짜 정보판 — 원/달러 환율 (과제 4)

매일 바뀌는 USD/KRW 환율 한 값을 기록하고, 그 값이 언제·어디서 왔는지, 데이터가 안 올 때는 왜 안 오는지를 함께 보여주는 정보판입니다.

## 공개 심사 주소

- 결과물: https://terran1234.github.io/daily-board-04/
- 소스: https://github.com/terran1234/daily-board-04

로그인·계정·비밀키 없이 열립니다.

## 카드 1 — 값이 뜻하는 바

| 항목 | 내용 |
|---|---|
| 값 | 달러(USD) 1개를 사는 데 필요한 원화(KRW) |
| 단위 | KRW per 1 USD |
| 출처 | ExchangeRate-API 공개 엔드포인트 `https://open.er-api.com/v6/latest/USD` (키 없음) |
| 출처 시각 | 응답의 `time_last_update_unix` — 출처가 값을 갱신한 때 |
| 조회 시각 | 이 화면(또는 기록 스크립트)이 값을 받아온 때 |
| 기준 시간대 | KST (Asia/Seoul, UTC+9) |

출처 시각과 조회 시각은 다른 시각입니다. 출처는 하루 한 번쯤 갱신하고, 화면은 열 때마다 조회합니다.

## 정상 한 건의 원자료 · 저장값 · 화면값 대조

2026-09-30 KST에 받은 정상 응답 한 건입니다. 세 값은 같습니다.

| 단계 | 어디에 있나 | 값 | 시각 |
|---|---|---|---|
| 1. 원자료 (받은 그대로) | [`data/raw/2026-09-30.json`](data/raw/2026-09-30.json) 의 `rates.KRW` | `1353.681844` | `time_last_update_unix` = `1790726551` → 2026-09-30 09:02:31 KST |
| 2. 저장값 | [`data/latest.json`](data/latest.json) 의 `value` | `1353.681844` | `source_time_kst` = `2026-09-30T09:02:31+09:00`, `fetched_at_kst` = `2026-09-30T17:26:04+09:00` |
| 3. 화면값 | 결과물 화면 "정상 한 건 대조" | `1,353.68` | 출처 시각 2026-09-30 09:02:31 KST |

- 원자료 − 저장값 = 0
- 저장소의 `data/raw/2026-09-30.json`은 자동 기록(GitHub Actions)이 2026-09-30 17:26 KST에 받은 응답 본문 그대로입니다(2968바이트, 끝 줄바꿈 없음, SHA-256 `66665b3c0e181ce66449d2bbf6aea07337998520201259a41dbb6d4196c941c2`). 같은 날 다시 조회한 것이라 값(`1353.681844`)과 출처 시각(`1790726551`)은 그대로이고, 조회 시각과 응답 안의 `time_next_update_unix`만 달라졌습니다.
- (이전에는 GitHub 웹 화면에서 파일을 폴더로 옮기며 끝 줄바꿈이 붙은 사본이 있었지만, 위 자동 기록이 같은 날 파일을 응답 그대로 다시 저장해 대체했습니다.)
- 화면값 규칙: 저장값(전체 자릿수)을 소수 둘째 자리까지 반올림해 표시합니다.
- 화면은 이 저장 기록을 실제로 읽어 와 세 값이 같은지 스스로 확인하고, 다르면 "일치하지 않습니다"를 띄웁니다.

## 카드 5 — 실제 이틀과 어제 대비

**상태: 서로 다른 KST 날짜의 실제 기록 3건 (2026-09-30, 2026-10-01, 2026-10-02). 플랫폼 영수증 증빙 2건은 마지막 두 날짜(10/1, 10/2)입니다.** 값은 모두 실제 공개 원천에서 실제로 조회한 것이고, 만들어 채운 값은 없습니다. 첫째 날(9/30)은 플랫폼 과정 기록을 남기기 전에 지나가서, 영수증 2건은 10/1과 10/2에 남깁니다(아래 "플랫폼 과정 기록").

**어제 대비 변화 (조회 날짜순, 같은 계산 규칙)**

- 변화 = 오늘 − 어제, 비율 = 변화 ÷ 어제 × 100.
- **2026-10-01 → 2026-10-02 (최신, 영수증 2건 기준)**: `1360.202164 − 1355.838011` = **`+4.364153`** (화면 표시 **+4.36원**), 비율 `+0.321879%` (화면 **+0.32%**).
- 2026-09-30 → 2026-10-01: `+2.156167` (+0.159282%).
- 결과물 화면의 두 곳(위쪽 보드의 "어제 대비" 줄, "04 실제 일별 기록과 어제 대비")은 항상 가장 최근 두 날짜로 계산해 같은 값을 보여 주며, 화면은 저장값으로 계산한 변화와 원자료 두 개로 다시 계산한 변화가 같은지 스스로 확인합니다(✓).
- 화면과 별도로 저장소의 원자료 파일을 직접 받아 다시 계산해 같은 값을 얻었습니다(차이 `4.364153`, 비율 `0.321879%`, 저장값=원자료, 관측 시각 일치, 조회 시각의 KST 날짜가 서로 다름).

**기록이 만들어진 과정 (있었던 일 그대로)**

- 2026-10-01 둘째 날 기록은 10:26 KST에 GitHub Actions를 수동 실행(`workflow_dispatch`)해서 남겼습니다. 예약 실행(10:20 KST)이 그때까지 뜨지 않았고, 이후 16:11 KST에 예약 실행이 돌아 같은 날 줄을 갱신했습니다.
- 2026-10-02 09:17 KST에 수동 실행했을 때, GitHub 실행 환경이 출처에서 **아직 어제 값**(`1355.838011`, 관측 시각 `2026-10-01T00:02:31Z`)을 받아 10/2 줄에 잘못 저장했습니다. 같은 시각 제 브라우저에서는 오늘 값 `1360.202164`가 보였습니다(출처의 캐시가 서버마다 다르게 갱신된 것으로 보입니다). 만들어 낸 값이 아니라 낡은 응답이었고, 영수증에 쓰기 전에 발견했습니다.
- 조치: ① `record-day.ps1`이 출처에 새 사본을 요청하도록 고쳤고(`Cache-Control: no-cache`, 요청 주소에 시각 인자 추가, 저장되는 출처 주소에는 인자를 넣지 않음), ② **새 날짜 줄은 출처 관측 시각이 이전 기록보다 새로울 때만 만들도록** 안전장치를 넣었으며, ③ 같은 날 줄을 갱신하는 규칙으로 10/2 줄을 오늘 값으로 바로잡았습니다(09:23:05 KST). 잘못 저장된 중간 커밋은 Git 기록에 남아 있습니다.
- 서로 다른 날짜는 3건까지만 저장하도록 상한을 걸어 두었습니다(아래 "플랫폼 과정 기록" 참고).

### 둘째 날은 어떻게 기록되나

- GitHub Actions(`.github/workflows/record.yml`)가 매일 01:20 UTC(= 10:20 KST)에 `record-day.ps1`을 실행합니다. 출처는 하루 한 번(약 00:02~00:15 UTC = 09:02~09:15 KST) 값을 갱신하므로 그 뒤 시각입니다.
- 비밀값은 없습니다. 출처가 키 없이 열려 있고, 저장소에 쓰는 것은 그 실행이 받는 임시 토큰뿐입니다.
- 같은 KST 날짜에 다시 실행하면 새 줄이 아니라 같은 줄이 갱신됩니다(카드 4 규칙).
- 서로 다른 KST 날짜는 **3건까지만** 보존하도록 스크립트에 상한(`-MaxDays 3`)을 뒀습니다. 과제의 실제 증빙은 서로 다른 날짜 2건이고(아래 "플랫폼 과정 기록"), 첫째 날(9/30)은 영수증을 남기기 전에 지나가서 첫째 날 + 영수증 2건(10/1, 10/2)으로 3건입니다. 이미 있는 날짜의 갱신은 항상 허용합니다. 처음에는 상한을 2건으로 뒀다가 이 사정 때문에 3건으로 바꿨습니다.
- 응답이 정상 성공이 아니면 아무것도 저장하지 않습니다.

자동 기록은 2026-09-30에 GitHub Actions에서 수동 실행(`workflow_dispatch`)으로 한 번 시험했고 성공했습니다. 봇 계정(`github-actions[bot]`)이 `data/daily.json`(1줄)과 `data/raw`·`data/latest.json`을 커밋했습니다. 아래는 기록 스크립트를 합성 시계로 시험한 결과입니다(임시 폴더에서만 실행, 실제 `data/`는 건드리지 않음).

| 시험 | 결과 |
|---|---|
| 1일차 00:00Z (KST 09:00) | 새 줄, 행 0 → 1 |
| 같은 날 09:00Z, 14:59:59Z 두 번 더 | 같은 줄 갱신, 행 1 → 1 → 1 |
| 15:00:00Z (KST 다음 날 00:00) | 새 줄, 행 1 → 2 |
| 세 번째 다른 날짜 (처음 상한 2로 시험) | 건너뜀(상한), 행 2, 파일 안 만듦 |
| 상한 3으로 바꾼 뒤: 셋째 날짜 / 같은 날 다시 / 넷째 날짜 | 새 줄(행 2 → 3) / 같은 줄 갱신(3 → 3) / 건너뜀(행 3) |
| 둘째 날 다시 실행 | 같은 줄 갱신, 행 2 → 2 |
| `result` 가 `error` 인 응답 | 오류로 중단, 아무것도 저장 안 함 |
| `KRW` 가 문자 `"1300"` 인 응답 | 오류로 중단, 아무것도 저장 안 함 |

### 어제 대비 계산 규칙

- 조회 날짜(KST)순으로 두 저장값을 놓고 **변화 = 오늘 − 어제**, **비율 = 변화 ÷ 어제 × 100**.
- 화면은 저장값으로 계산한 변화와, 원자료 두 개(`data/raw/…`의 `rates.KRW`)로 다시 계산한 변화가 같은지 확인하고, 위쪽 보드의 "어제 대비" 표시와도 맞춰 봅니다.
- 위 "실제 기록 3건과 어제 대비" 표가 그 결과입니다.

### 플랫폼 과정 기록 (선택 · 영수증)

제출 플랫폼의 카드 5에는 "실제 공개 원천 기록"을 남기는 선택 기능이 있습니다. 제출·승인을 막지는 않지만, 채점의 C22~C24가 이 기록(플랫폼이 서버 날짜 Asia/Seoul로 시각을 찍음)의 서로 다른 날짜 2건을 앱의 저장값·화면값과 대조합니다. 그래서 날짜가 다른 두 건을 남깁니다. 플랫폼 기록은 서버 날짜로 찍히기 때문에 지난 날짜(9/30)는 나중에 남길 수 없습니다.

## 카드 4 — 하루 한 줄

결과물 화면의 "03 하루 한 줄 — 같은 날은 한 건"에서 합성 시계로 재생합니다. 날짜·시각·값(`pt`)은 시험용이며 실제 환율 기록에는 영향을 주지 않습니다.

### 일별 고유키와 갱신 규칙

- **고유키** = `signal_id` + `Asia/Seoul` 날짜(`record_date`). 조회 시각 `fetched_at`(UTC)을 KST로 바꿔 정규화할 때 한 번만 만듭니다. 브라우저 지역 시간이나 UTC 날짜는 쓰지 않습니다.
- **같은 키**: 새 줄을 만들지 않고 저장값과 `last_fetched_at`만 갱신합니다. `record_id`와 `first_fetched_at`은 유지합니다.
- **다른 키**(다음 KST 날짜): 새 줄을 만듭니다.
- **저장 전 검증**: `record_date`가 `fetched_at`의 KST 날짜와 다르면 거절합니다(날짜 키를 잘못 만든 입력 차단).
- 구현 위치: `engine.js`의 `applySuccessfulReading`(갱신 규칙)과 `runDailySeries`(시험 기록).

### 같은 날 재실행 전후 행 수 (C20 · C21)

| 단계 | 조회 시각 (UTC) | KST 시각 | 날짜 키 | 동작 | 행 수 (전 → 후) | 저장값 |
|---|---|---|---|---|---|---|
| 1회차 (fixture `T04-NORMAL-D1-A`) | 2026-08-24 00:00:00 | 2026-08-24 09:00:00 | 2026-08-24 | 새 줄 | **0 → 1** | 100 |
| 2회차 (fixture `T04-NORMAL-D1-B`) | 2026-08-24 09:00:00 | 2026-08-24 18:00:00 | 2026-08-24 | 같은 줄 갱신 | **1 → 1** | 105 |
| 3회차 (직접 만든 합성 재실행) | 2026-08-24 14:59:59 | 2026-08-24 23:59:59 | 2026-08-24 | 같은 줄 갱신 | **1 → 1** | 107 |

### 자정 근처 — UTC와 KST 날짜 대조

KST 00:00~08:59는 UTC로는 아직 전날입니다. 날짜 키를 UTC로 만들면 하루가 어긋납니다.

| 단계 | 조회 시각 (UTC) | UTC 날짜 | KST 시각 | 날짜 키 (KST) | 동작 | 행 수 |
|---|---|---|---|---|---|---|
| 기준 | 2026-08-24 00:00:00 | 2026-08-24 | 2026-08-24 09:00:00 | 2026-08-24 | 새 줄 | 0 → 1 |
| 자정 1초 전 | 2026-08-24 14:59:59 | 2026-08-24 | 2026-08-24 23:59:59 | 2026-08-24 | 같은 줄 갱신 | 1 → 1 |
| 자정 정각 | 2026-08-24 15:00:00 | 2026-08-24 | 2026-08-25 00:00:00 | 2026-08-25 | 새 줄 | 1 → 2 |
| 날짜 키를 UTC로 잘못 만든 입력 | 2026-08-24 15:00:01 | 2026-08-24 | 2026-08-25 00:00:01 | 2026-08-24 | **거절** (KST 날짜와 다름) | 2 → 2 |

UTC 날짜는 자정 정각에도 그대로 08-24인데 KST 날짜는 08-25로 넘어가 새 줄이 생깁니다. UTC 날짜로 키를 만든 입력은 저장 전에 거절되어 행 수가 그대로입니다.
